企業環境焦點

系統 Proxy 選用、受管網路條件、人工核准規則與同一端點的連線提示序列化，都是企業 Windows 導入前要拿實際帳號、網段與政策驗證的項目。

Windows Codex 相關消息摘要

  • 0.167.0 正式版：官方標示為 latest。可用 codex agents --no-daemon 開啟 agent command center；終端 session picker 可在已連接後端間切換並保留草稿。
  • Windows 系統 Proxy：在 /experimental 中可選擇使用 macOS 或 Windows 的系統 Proxy 設定。這是「可選用」能力，不代表所有 PAC、TLS 攔截、整合式驗證或服務帳號情境已自動相容。
  • 本機圖片附件：支援的終端可在撰寫時預覽本機圖片附件，也可從可點擊的 transcript 路徑開啟已檢視圖片；這對需要看截圖、錯誤畫面或操作證據的 Windows 技術流程較實用。
  • 受管網路與人工核准：app-server README 補充 [permissions.network] 的受管網路限制，以及需要重新由人員核准的 prompt-user command rule；網路核准提示會在請求結束後關閉，同一端點的同時請求則逐一提示。
  • 正式／預發版邊界：0.168.0-alpha.7、0.169.0-alpha.2 是 pre-release。正式環境仍應固定 0.167.0，先完成測試、記錄與回退設計。

對 MIS / Windows 使用者的影響

系統 Proxy 選項讓桌面端採用既有 Windows 網路設定的路徑更清楚，尤其適合先在使用者帳號的受控端點驗證。但 SCCM、工作排程與服務帳號往往不具備相同使用者設定；PAC、WinHTTP Proxy、瀏覽器 Proxy 和環境變數也可能不同，不能用互動式成功結果推論背景執行一定可行。

受管網路和重新人工核准的規則，讓 IT 可以將「哪些網域可連、哪些操作要再確認」寫進可審查的流程。建議把這些規則與既有防火牆、代理、端點防護和變更管理一起盤點，保留拒絕與逾時的 log，才有能力釐清連線失敗是工具、網路還是政策所致。

值得注意的地方

  • 本文已揭露本週繁中第一手技術資料有限；社群與第三方安裝教學僅作為需求訊號，不用來宣稱版本功能或企業相容性。
  • 「系統 Proxy」不是單一設定的同義詞。應分別驗證使用者互動、SYSTEM、排程與遠端工作階段，且不要在測試紀錄中留下 Proxy 密碼或存取權杖。
  • 本機圖片預覽提高操作效率，也可能使截圖中的帳號、內網名稱或機密內容進入工作脈絡；導入時應先建立脫敏與可上傳資料的規範。
  • Alpha 版本只應在隔離環境驗證。保留 stable 安裝包、設定快照、測試記錄與可復原版本，避免問題發生時只剩「更新看看」。

我的實務看法

本週最有價值的不是多一個指令，而是 0.167.0 讓 Windows 現場的兩件事更可操作：沿用系統 Proxy 的能力，以及把網路／人工核准條件明文化。對 MIS 而言，這正好把導入重心從「能不能安裝」移到「是否能被控制、記錄與回復」。

我的建議順序是：固定 0.167.0 與受信任安裝來源，選一台測試 Windows 端點，在一般使用者帳號下驗證 HTTPS、WebSocket 與系統 Proxy；再另測 SYSTEM 或排程情境。接著以低風險、可審查的工作區試行圖片附件與權限提示。若代理驗證、核准紀錄與回退都過關，再考慮擴大使用範圍。

結論

過去一週雖缺少大量繁中 Windows Codex 第一手報導，但官方 0.167.0 提供了明確的企業導入訊號：可選用 Windows 系統 Proxy、強化受管網路與人工核准的說明，並改善終端的本機圖片工作流。對 MIS 團隊，下一步應是分情境驗證帳號、Proxy、網路政策與資料處理邊界，而不是直接把正式版推向所有端點。

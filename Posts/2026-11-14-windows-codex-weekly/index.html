Windows 原生路徑

官方 Windows Sandbox 文件指出桌面 App 可在 PowerShell 原生執行，並可依裝置與組織政策使用 MXC、elevated 或 unelevated 實作；版本升級後仍須依實際權限與網路政策驗證。

Windows Codex 相關消息摘要

  • 0.169.0 正式版：官方 GitHub release 標示為 latest。新增終端工作區的多個 side-chat 分頁、舊任務搜尋，以及診斷 ZIP 的本機儲存功能。
  • Windows Sandbox 修正：修正含引號 cmd.exe 路徑的處理，也修正當 PowerShell 工作目錄的父資料夾不可讀時的 sandbox 行為。這直接關係到 Windows 路徑、ACL 與以 PowerShell 啟動的實務情境。
  • 信任目錄界線：codex exec 在不受信任目錄中會保持停用專案設定與 MCP server，即使使用 --sandbox workspace-write 亦然；需以 --trust 明確儲存信任。這是降低隨意進入未知 repo 時自動載入設定風險的補強。
  • Windows Sandbox 文件：官方說明將 MXC 列為相容裝置上的建議實作；舊式 elevated 與 unelevated 為後備選項。前者需要管理員核准設定，後者的網路隔離較弱且不支援 denied read paths。

對 MIS / Windows 使用者的影響

這次修正雖不像新功能那樣顯眼，卻碰到企業端最容易放大的兩個邊界：路徑引用與 ACL。若命令列包裝、軟體部署或工作目錄位於受控路徑，含空白或引號的執行檔路徑與父資料夾讀取權限，都可能使「在開發者電腦可用」與「在受管端點失敗」產生落差。

對 MIS 而言，升級評估應把 Windows 使用者、系統管理員、SCCM／工作排程帳號分開測試；三者的路徑、ACL、Proxy 與互動狀態通常不同。Sandbox 類型也要先符合資安政策，再討論自動化範圍，不能只用一般使用者互動成功就視為完成驗收。

值得注意的地方

  • 本文已揭露本週繁中第一手資料有限；社群貼文與第三方文章只用於觀察採用訊號，不用來宣稱版本功能或企業相容性。
  • 修正不等於所有路徑與 ACL 組合都已相容。請用實際的受管安裝路徑、受限父資料夾與 PowerShell 啟動方式做回歸測試，並保留可供稽核的 log。
  • --trust 是明確擴大信任邊界的動作；在未知 repo 或外部來源工作區，先檢查專案設定與 MCP 組態，避免把信任判斷交給便利性。
  • MXC、elevated 與 unelevated 的隔離能力不同。採用後備模式前，應由資安與端點團隊確認其檔案與網路限制是否符合內部政策。

我的實務看法

本週最值得做的不是立即全面更新，而是把 0.169.0 視為 Windows 相容性回歸測試的觸發點。它明確修正了 Windows sandbox 的引號路徑與不可讀父目錄處理，剛好是企業桌面常見、又容易被一般開發環境忽略的條件。

建議先固定 0.169.0 與受信任安裝來源，建立三組測試：一般使用者 PowerShell、管理員 PowerShell、以及非互動式部署帳號；每組都涵蓋正常工作目錄、受限父目錄與帶引號的程式路徑。確認 sandbox、網路核准與失敗 log 均可預期後，再逐步擴大到正式使用者群組。

結論

本週繁中 Windows Codex 資料量有限，但官方 0.169.0 提供了一個清楚的 Windows 維運訊號：沙箱對特定 cmd.exe 引用和 PowerShell 工作目錄權限的處理已獲修正。MIS 團隊下一步應以真實路徑、ACL、帳號與 sandbox 政策驗證升級結果，並繼續把「信任設定」當成可控且可稽核的決策。
